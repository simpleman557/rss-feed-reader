# Feed Reader — Spec

A self-hosted, minimal alternative to Feedly. Local-first in the sense of no user accounts and no third-party services — but persistence lives in a SQLite database owned by the server, not the browser, so subscriptions and read state survive clearing browser data and aren't tied to one browser profile. Built to run in Firefox first, with mobile-browser use as a secondary goal.

## Architecture

**`server/`** — Node/Express. No file-watching — restarting it (`Ctrl+C` then `npm start`) is required to pick up any backend code change; unlike the Vite frontend, there's no hot-reload here.
- Owns all persistent data — categories, feeds, articles, read/saved state — in a single SQLite file, `feed-reader.db` (via `better-sqlite3`), kept in an OS-appropriate user data directory *outside* the project/install directory — see Data Directory below. `server/src/db.js` itself is now just wiring: opens the real connection, runs migrations, and binds it to the business logic. That logic — every ordering/uniqueness rule (`addCategory`, `addFeed`, `renameFeed`, etc.) — lives in `server/src/dbLogic.js`'s `createDb(db)` factory, with the handful of functions that need no database at all (`normalizeFeedUrl`, `findAlphabeticalOrder`, `uniqueTitleInBucket`, …) pulled out further still into `server/src/dbHelpers.js`. Schema/data migrations are `server/src/migrations.js`'s job (see Migrations below); the retention purge is `server/src/retention.js`'s (see Retention & Purge below). All of this was split out of `db.js` specifically so none of it has a module-level database connection of its own and each piece can be unit-tested against a throwaway database instead of the real one (see Testing below).
- `addFeed` rejects a URL that doesn't parse or isn't http/https before storing it. Not a security boundary (safeFetch is), just so a typo fails immediately with a clear message instead of being saved and then failing on every refresh forever.
- `server/src/feedParser.js` — fetches an RSS/Atom URL server-side (avoids the browser CORS restriction that blocks fetching arbitrary third-party feeds directly from client JS), parses it with `rss-parser`, and returns normalized data: `{ title, feedImageUrl, link, feedWideImageUrl, items: [{ title, link, guid, isoDate, contentSnippet, imageUrl }] }` (`feedWideImageUrl` is non-null only for an icon-only feed — see Per-article images). Called from the refresh routes below, so there's one implementation, not two. There was previously also a `GET /api/feed?url=<feedUrl>` route exposing this over HTTP, added for a preview-before-adding flow the frontend never ended up using. It was removed: nothing called it, and an endpoint that fetches any URL a caller names is a server-side request forgery (SSRF) primitive — it let a caller use this server to reach loopback and LAN addresses their own browser can't, and the distinguishable error messages made it a working internal port scanner.
- `server/src/feedWideImage.js` (`dominantFeedImageUrl`) and `server/src/trackingPixel.js` (`isTrackingPixel`) — two small, pure, side-effect-free helpers that reject images which aren't really per-article pictures before they can be stored: a logo repeated across a whole feed, and a tracking pixel (see Per-article images below). Shared by `feedParser.js` (dropping them at ingest) and `migrations.js` (clearing ones already stored).
- `server/src/faviconResolver.js` — discovers each feed's real site icon by fetching its homepage and reading its actual `<link rel="icon">`/`apple-touch-icon` declarations, validating whatever it finds before trusting it (see Feed Icons below). Invoked from `refreshFeed.js` on a feed's first sync, then periodically re-run (every 30 days) rather than on every refresh — see `shouldDiscoverIcon`.
- `server/src/opmlImport.js` (`planOpmlImport`) — turns the outline tree the browser parsed from an OPML file into a flat plan (which feeds go in which category, which entries are invalid) — pure, no database or network, and applied by `importOpml` in `dbLogic.js`; see Export & Import (OPML) below. `server/src/settleWithConcurrency.js` is the small helper `POST /api/refresh` uses to fetch at most 10 feeds at a time (see Auto-refresh).
- `contentSnippet` (used as the "one sentence more than the headline") comes straight from the feed's own description/summary field, truncated to 280 chars — no AI summarization involved.
- Persistence routes under `/api/categories`, `/api/feeds`, `/api/articles`, and `/api/refresh` — see **API** below.
- `fetchAndParseFeed()` fetches the feed XML itself via Node's built-in `fetch()` (with a non-browser `User-Agent`, `FeedReader/1.0`) and hands the text to `rss-parser`'s `parseString()`, rather than letting `rss-parser` fetch the URL itself (it uses Node's older `http`/`https` module internally). Some sites block that older client outright regardless of headers sent — confirmed to be connection/TLS fingerprinting, not a `User-Agent` check, since Node's `fetch()` gets through with no special headers at all. The `User-Agent` is deliberately non-browser-like: sites running AWS WAF bot challenges see a browser-like UA, demand a JS challenge the server can't execute, and return an empty `202` with `x-amzn-waf-action: challenge` — a non-browser UA skips the challenge entirely and gets the feed. Guard rails for this case (WAF header detection, empty-body check) are in place as a fallback. The UA trick is not enough from a cloud host: some sites' WAFs challenge requests from data-center IP ranges (e.g. Cloud Run) whatever the UA, so one site's challenged league feeds (a fixed set of its RSS URLs) are read from that site's public JSON news API instead by the site-specific adapter `server/src/espnNews.js`. It keeps only the item types the RSS carries (`Story`, `HeadlineNews`) and the RSS guid format (`US-EN-<id>`), so the two sources never duplicate an article. Locally the RSS feed is still what's used. Any other challenged feed reports "Blocked by bot protection — the site refuses automated requests from this server".
- Optionally serves the built frontend too (`express.static` on `web/dist`, only mounted when that directory exists) — see Running It below for the single-process vs. two-process dev workflows this supports.
- **Bounded parsing of remote content.** Everything fetched above is attacker-influenced, and Node is single-threaded, so any superlinear work on it stalls the entire server. Two patterns that scanned remote HTML were rewritten: the icon-link regex in `faviconResolver.js` (27 KB of crafted HTML took 10s, growing ~7x per doubling) and `firstImgSrc` in `feedParser.js` (293 KB took 6.5s, quadratic). Both had unbounded quantifiers either side of a literal; both now match a length-bounded tag and pick attributes out of the captured tag separately, which removes the nesting — the same inputs are now 4.7ms and 148ms, flat beyond the scan caps. Response bodies are also size-capped as they stream (`readTextCapped` / `readArrayBufferCapped` in `safeFetch.js`: 5 MB feed, 2 MB homepage, 5 MB icon), since Content-Length is a hint rather than a promise and nothing otherwise stops a server from streaming until memory runs out. A third instance of the same problem lived inside `rss-parser` itself, and was the worst of the three: its `utils.stripHtml` (`lib/utils.js`) has the same unbounded-quantifier shape, and it runs on every item's content during parsing to build `contentSnippet` — 100 KB of hostile content took 1.4s and 400 KB took 23.8s, while XML-parsing the same feed took ~2ms, so `xml2js` was never the problem. It can't be skipped or configured off, and a size cap can't bound it (capping low enough to help would reject real feeds), so `server/src/stripHtml.js` replaces it with a linear version, installed from `feedParser.js` by swapping the property on rss-parser's shared `utils` object. The replacement reproduces the original's output exactly — including its quirks, such as a match running past a `>` that is followed by a newline and swallowing the text up to the next tag — so no feed's snippets change: a seeded differential test checks 30,000 generated tag soups against a verbatim copy of the original, and 4,176 strings (966 KB) of content from ten live feeds produced zero differences. `feedParser.js` throws on startup if that internal function ever goes missing, so an rss-parser upgrade can't quietly bring the stall back.
- `server/src/safeFetch.js` — every outbound fetch (the feed URL, a feed's declared homepage, a candidate icon) goes through this rather than calling `fetch()` directly. It resolves each target and refuses non-public addresses (loopback, RFC1918, link-local/cloud-metadata, CGNAT, multicast), and re-runs that check on **every redirect hop** — validating only the URL passed in would be pointless, since a public-looking URL that `302`s to `127.0.0.1` defeats it. Redirects can't simply be banned, because feeds legitimately use them (FeedBurner → publisher, http → https, moved domains), so each hop is checked instead, up to 5. Real feeds are public, so nothing legitimate is affected. Matters because the URLs involved aren't all the user's: a feed's homepage comes from its own `<link>` element and the icon href from that page's HTML, meaning the feed publisher would otherwise choose where this server sends requests. Checking the *resolved* address rather than the hostname text also handles obfuscated literals (`http://2130706433/`) for free, and the IPv6 rules cover every way an internal IPv4 address can ride inside an IPv6 one — IPv4-mapped (`::ffff:127.0.0.1` and its hex form `::ffff:7f00:1`), IPv4-compatible, and NAT64 `64:ff9b::/96` — by pulling out the embedded address and applying the IPv4 rules to it. `isPublicUrl` exposes the same check without making a request, for URLs that get stored and later loaded by the browser rather than fetched here: `refreshFeed.js` runs a feed's own `<image><url>` through it before saving it as the feed icon, so a hostile feed can't make the browser hit `http://192.168.1.1/...` on every page load (an `<img src>` the user's browser would otherwise request). The one gap, deliberately documented in the file rather than papered over: DNS rebinding, which would need socket-level IP pinning to close — and, for the stored-image case, the browser does its own DNS resolution, so a hostname resolving differently there isn't covered; IP literals and ordinary hostnames are.

**`web/`** — Vite + React SPA.
- Dev server proxies `/api/*` to `http://localhost:3001` (see `vite.config.js`), so the frontend never needs to know the backend's port directly.
- Holds no persistent data of its own. `web/src/data/db.js` is a thin `fetch()`-based client exposing the exact same function names/signatures the UI has always called (`getCategories()`, `addFeed()`, `markRead()`, etc.) — only the implementation changed, from local IndexedDB calls to HTTP requests, so `App.jsx`/`Sidebar.jsx`/`ArticleList.jsx`/`ArticleItem.jsx`/`TopBar.jsx` needed no changes at all. `web/src/data/feeds.js` similarly wraps the two refresh endpoints.
- A single breakpoint at 768px: above it, the sidebar is a fixed 260px independently-scrolling left column; below it, the sidebar is an off-canvas drawer opened from a ☰ button in the top bar (see Design decisions), so articles fill the screen. Touch devices (`pointer: coarse`) get 44px tap targets and 16px form fields at any width.

Validation errors (duplicate/reserved category name, duplicate feed URL, duplicate manually-renamed feed title) respond `400 { error: "message" }`, using the same message text the app has always shown; `web/src/data/db.js` throws `Error(body.error)` on any non-OK response so the existing `window.alert`-on-catch handling in `Sidebar.jsx` keeps working unchanged.

`POST /api/refresh` (hit by both the manual Refresh button and the auto-refresh timer) and `POST /api/feeds/:id/refresh` (hit right after adding a feed) do the entire fetch-and-persist cycle server-side — the browser no longer orchestrates a per-feed loop itself, since both the fetching and the storage now live on the server anyway.

## Per-article images

Most RSS/Atom feeds embed a per-article image in one of several incompatible ways, with no single standard — `server/src/feedParser.js`'s `itemImageUrl()` tries each, in order of how explicit the signal is:

1. `media:thumbnail` — an explicit "this is the thumbnail" tag (common in news-site feeds).
2. `media:content` — only when it's actually an image, so a video/audio `media:content` entry isn't mistaken for a picture: either declared as one (`medium="image"` or a `type` starting `image/`, as many news sites do), or, when an entry declares neither (both attributes are optional in Media RSS), when its URL path ends in an image extension (`jpg`/`jpeg`/`png`/`gif`/`webp`/`avif`). Every `media:content` entry is checked, not just the first.
3. `itunes:image` — per-item podcast art; `rss-parser` decorates this automatically whenever the feed declares the itunes namespace, no extra config needed.
4. `enclosure` — only when its `type` is `image/*`, so a podcast's audio enclosure isn't misread as an image.
5. The first `<img>` found in the item's full HTML content (`content:encoded`, common in public-radio and news feeds — this field isn't exposed by `rss-parser` by default and needed explicit `customFields` config to access).
6. The first `<img>` found in plain `description` HTML (some tech-news feeds don't populate `content:encoded` at all).
7. `null` if none of the above yield anything.

Two kinds of image are rejected before they can be mistaken for a per-article photo, because both load fine in the browser (so a broken-image fallback can't catch them) and would otherwise render as junk. **Tracking pixels** — a 1×1 telemetry GIF/PNG some feeds embed as the first `<img>` in every item (e.g. `.../tracking/some-rss-pixel.png?story=…`) — are skipped by `firstImgSrc` via `isTrackingPixel` (`server/src/trackingPixel.js`, matched on well-known signatures only — a `/tracking/` path, a bounded `pixel`/`beacon` token, `1x1`, a named spacer gif — so a real photo whose URL merely contains one of those words isn't swallowed), so the scan falls through to a real content image or to `null`. **Feed-wide logos** — the same image repeated across (nearly) every entry, which is the feed's own logo/social-card rather than a per-article picture (one real feed stamped the same social-card PNG onto all 95 of its items) — are detected by `dominantFeedImageUrl` (`server/src/feedWideImage.js`: one URL covering ≥70% of a feed's ≥5 image-bearing items; measured across the subscribed feeds, real feeds share ~2% at most while the offending feed shared 100%, so the margin is wide) and dropped from those items. `fetchAndParseFeed` returns the offending URL as `feedWideImageUrl`, which marks the feed as **icon-only**.

A refresh also fills in images for articles that are already stored: `upsertArticles` (`dbLogic.js`) leaves an existing row untouched except that a missing `imageUrl` is set when the feed now supplies one. That way an improvement to extraction reaches older articles too. A stored image, whether from the feed or `og:image`, is never replaced, and `read`/`saved` state is never touched.

Some feeds don't include image data in any of these forms — the image only appears as an `og:image` Open Graph tag on the live article page. `server/src/ogImageFetcher.js` fills these in as a fire-and-forget background pass after each refresh: for any article that has no `imageUrl` yet and hasn't been checked before (`ogImageChecked IS NULL`), it fetches the article's own page, reads the first 32 KB (enough to cover `<head>` for any real page), and extracts the `og:image` tag. The refresh response goes out immediately — the pass never delays it. The result is stored permanently in `articles.imageUrl` and `ogImageChecked` is stamped, so the article page is never re-fetched on future refreshes regardless of success or failure — one attempt per article. A 5-second timeout and silently swallowed errors mean a slow or broken article page can't delay or crash the batch. The found URL is validated through `isPublicUrl` (the same SSRF guard used everywhere else) before being stored, so a hostile article page can't inject a private-network image URL. **Icon-only feeds are excluded from this pass**: since every article legitimately has no per-article image, backfilling `og:image` would just repopulate them — such a site's article pages may carry per-*topic* badge `og:image`s — so `refreshFeed.js` skips the pass for such a feed and clears any images already stored for it (`clearArticleImagesForFeed`), leaving every article on the one clean feed icon. That uniform clean favicon was chosen deliberately over the scattered per-topic badges.

`ArticleItem.jsx` resolves each row's image through an ordered, best-first fallback: the article's own image (`article.imageUrl`, shown with `object-fit: cover` / `.article-image--photo` — photos vary enough in composition that covering the row's image slot reads better than letterboxing), then the feed's clean site icon (`feedImageUrl`, `object-fit: contain` so a logo keeps its full shape), then `PLACEHOLDER_ICON`. The slot itself is 92px wide and stretches (`align-self: stretch` in the row's grid — see Main content area below) to match whatever height that row's two-line title/snippet block ends up needing, so it isn't a fixed square the way the 40×40 tile it replaced was. Each candidate's `onError` records that URL as failed (keyed on the URL, not an index, so a later refresh swapping in a new image is retried) and advances to the next, so an article image that 404s or is hotlink-blocked — or a stray non-URL like a literal `"undefined"` — lands on the clean feed icon rather than skipping straight to the grey placeholder. `upsertArticles` uses `INSERT OR IGNORE`, so an article already stored keeps whatever `imageUrl` it got on first fetch — a backend extraction-logic improvement only benefits articles fetched after it, which is why the icon-only and tracking-pixel cleanups also ship as migrations that backfill existing rows (below).

## Feed icons

Every sidebar feed entry shows the feed's own site icon (`feedImageUrl`). Article rows prefer a per-article photo (`article.imageUrl` — see Per-article images above) when one is available, falling back to the feed icon, then to `PLACEHOLDER_ICON` on error. At the 92px-wide (article row) / 16×16 (sidebar) size this renders at, a scraped article photo varies too wildly in subject/crop to read as anything specific, while a consistent per-feed mark is recognizable at a glance; a brief exploration of generated letter-monogram tiles (solid-color initials) was tried and rejected once it became clear that manually guessing each publisher's brand color was error-prone (several guesses were simply wrong, and there's no way to know without checking) and unnecessary, since most feeds already had a usable real logo available.

**Rendering** (`ArticleItem.jsx` / `Sidebar.jsx`): a plain `<img src={feedImageUrl}>` falling back to `PLACEHOLDER_ICON` (a small inline SVG data URI, no separate asset file) on `onError`. The tile uses `object-fit: contain` (not `cover`) so a non-square logo is never cropped into an unrecognizable fragment, on a **fixed white background** (not the theme's `light-dark()` tokens) with a hairline border — most real-world favicons/logos are dark ink on a transparent or white backdrop, meant to sit on a light page, so a theme-flipped dark tile background would make them vanish in dark mode (this happened in practice with real logos before this fix).

**Discovering the actual icon** (`server/src/faviconResolver.js`, invoked from `refreshFeed.js`): a naive guess — the RSS feed's own declared `<channel><image>` (often an old wide wordmark banner sized for a 2000s-era feed-reader header, e.g. a 250×40 logo — illegible shrunk into a small square) or a same-origin `favicon.ico` guess (many current sites don't serve anything there and 301-redirect to the homepage instead) — breaks often enough that it's not trustworthy on its own. Instead, `discoverFeedIcon(siteUrl)` does what a real browser does: fetches the site's actual homepage HTML and reads its declared `<link rel="icon">` / `apple-touch-icon` tags (preferring the largest `apple-touch-icon`, since that's almost always a proper square mark rather than a tiny favicon or a wordmark banner), then validates each candidate before trusting it — rejecting anything that isn't a real image response, is suspiciously small (catches an abandoned near-blank placeholder stub — a real site's `favicon.ico` and `apple-touch-icon.png` were both literal 1×1px stubs), or only survives over plain HTTP (catches an HTTP-only legacy asset silently getting blocked by a browser that enforces HTTPS — one site's RSS image lived on a 2009-era subdomain whose HTTPS version just redirected back to HTTP, so it loaded fine in casual testing but was blocked outright by Firefox's HTTPS-Only Mode). Falls back to the naive guess (then to `PLACEHOLDER_ICON` client-side) if nothing declared on the homepage survives validation.

**Rechecking periodically, automatically** (`shouldDiscoverIcon` in `faviconResolver.js`): fetching and parsing a whole homepage is worth doing on every refresh — see the `feedImageUrl`/`iconCheckedAt` bullets under Data Model above for exactly when. Rather than gating solely on "is `feedImageUrl` still `NULL`" (which meant a feed with an already-decent-but-not-great icon could never pick up a later improvement to this file's ranking/validation logic, or a site's own icon change, without someone noticing and re-running a one-off script by hand), every feed also carries an `iconCheckedAt` timestamp of when discovery was last *attempted*. `shouldDiscoverIcon(feed)` returns true on a feed's first sync (`iconCheckedAt` still `null`) or once 30 days have passed since the last attempt — chosen deliberately generous, since a site rebranding its icon or this file's own logic improving are both rare, low-frequency events, and rechecking mostly-unchanged icons more often would just be wasted homepage fetches across every subscribed feed. If a recheck's discovery attempt comes back empty (e.g. the site was briefly down), `refreshFeed.js` falls back to the feed's existing `feedImageUrl` rather than the cheap RSS-derived guess, so a transient recheck failure can never downgrade an already-good icon — the guess is only ever used when there's truly nothing better yet. Fully automatic — no button, no endpoint, no manual script.

## Data Directory

`feed-reader.db` lives outside the project/install directory entirely, so updating or reinstalling the code never touches your data — the same reasoning real desktop apps use (e.g. macOS keeps app data in `~/Library/Application Support/`, not inside the `.app` bundle). Computed once in `server/src/dataDir.js`, in priority order:

1. `FEED_READER_DATA_DIR` environment variable, if set — an explicit override for anyone who wants the file somewhere specific (a synced folder, an external drive, etc). The Docker image sets it to `/data`, where Cloud Run mounts a GCS bucket (see `DEPLOY.md`).
2. Otherwise, an OS-appropriate default: `~/Library/Application Support/Feed Reader` on macOS, `%APPDATA%/Feed Reader` on Windows, `$XDG_DATA_HOME/feed-reader` (or `~/.local/share/feed-reader`) on Linux.

**One-time migration**: earlier versions stored the database inside the project directory (`server/data/feed-reader.db`). On startup, if nothing exists yet at the new location but the old file does, `dataDir.js` moves it (and its `-wal`/`-shm` SQLite sidecar files, which can hold not-yet-checkpointed writes) to the new location automatically, logging what it did — existing subscriptions and read/saved state survive the upgrade untouched. This is a one-shot check (skipped once a file exists at the new location), not an ongoing sync.

**Journal mode**: `db.js` uses SQLite's WAL mode by default. `SQLITE_JOURNAL_MODE` overrides it (validated against SQLite's modes) because WAL needs shared memory that network/FUSE filesystems such as the Cloud Run GCS mount don't provide, so that deployment sets `DELETE`.

## Migrations

Schema and one-time data changes are tracked with SQLite's built-in `PRAGMA user_version` — a single integer stored in the database file's own header, which is exactly what it's for, so no extra table or dependency is needed. `server/src/migrations.js` holds an ordered list of `{ version, name, run(db) }` migrations; `runMigrations(db)` (called once from `db.js`, right after opening the connection) reads the stored version, runs only the migrations numbered higher than it, in order, and bumps the version after each one succeeds — each inside its own transaction, so a failure leaves the database at its last-known-good version rather than half-applied.

There's deliberately no rollback tooling — a migration that throws crashes the app on startup rather than silently continuing against a schema the code doesn't expect, and for a single-user local tool, backing up the database file first (already this project's practice before anything risky— see Design decisions) is the accepted substitute for real rollback support. A full framework (Prisma/Knex-style, with rollback and branching) would be solving for a multi-environment risk profile this app doesn't have.

Every migration is also internally idempotent (checks before altering) even though the version tracker alone would normally make that redundant — this system was retrofitted onto a database that had already picked up some of its changes via older, ad-hoc guards before `migrations.js` existed (its `user_version` started at 0 even though migrations 1 and 2 had, in substance, already happened), so each one has to be safe to run again as a no-op. Adding a new migration means appending a new entry with the next version number; existing entries should never be edited once shipped, only appended after.

## Data Model (SQLite)

**`categories`** — `{ id, name, order }`
- `name` must be unique, case-insensitive, trimmed.
- `"Uncategorized"` (any case) is reserved — cannot be used as a real category name.
- `order` is a `REAL` column, auto-managed (see Ordering below); `NOT NULL` from creation, so — unlike the original IndexedDB version — there's no missing-value healing to worry about on read.

**`feeds`** — `{ id, url, categoryId, title, feedImageUrl, siteUrl, iconCheckedAt, order }`
- `categoryId` is always a real category id — every feed must belong to one (see Sidebar below for why "Uncategorized" was removed as a concept entirely). `addFeed`/`updateFeedCategory` both reject a missing or nonexistent `categoryId` (`requireCategory` in `dbLogic.js`), and `deleteCategory` refuses to delete a category that still has feeds in it (`"<name>" still has feeds in it — move or delete them first.`) rather than orphaning them. The column keeps `ON DELETE SET NULL` on its foreign key purely as a defense-in-depth fallback — through normal app use, that path should never actually fire.
- `title` starts out equal to `url` at creation time (a placeholder) and is overwritten with the feed's real title **only on the very first successful refresh** (while `title` still equals `url`) via `syncFeedMetadata` — every subsequent refresh leaves `title` alone, so neither the auto-synced title nor a later manual rename is ever silently reverted by a refresh.
- `siteUrl` is the feed's real homepage (parsed from the RSS `<link>` element, e.g. `https://www.example.com/sport` — often a different host than the feed URL itself, e.g. `feeds.example.com`). Re-synced on every refresh; exists purely so `faviconResolver.js` has something reliable to fetch (see Feed Icons below).
- `feedImageUrl` (the icon shown in the sidebar and next to every article from that feed — see Feed Icons below) is **not** unconditionally re-synced like it used to be, since discovery involves fetching the feed's homepage — not something to redo on literally every refresh. `refreshFeed.js` runs discovery (and so only touches `feedImageUrl`) on a feed's first sync, and periodically thereafter — see `iconCheckedAt` below and `shouldDiscoverIcon` under Feed Icons.
- `iconCheckedAt` records when icon discovery was last *attempted* for this feed (success or failure), regardless of whether it found anything. `shouldDiscoverIcon` (see Feed Icons) uses it to gate re-discovery to roughly once every 30 days per feed instead of on every refresh, so an already-populated icon can still automatically pick up a later improvement to `faviconResolver.js` or a site's own icon change — without anyone needing to notice and re-run a one-off script.
- If the title being auto-synced on that first refresh would collide with another feed's title already in the same category bucket (two different feeds can legitimately share a real-world title, e.g. two editions of the same publication), it's automatically disambiguated with a `" (2)"`, `" (3)"`, etc. suffix (`uniqueTitleInBucket` in `dbHelpers.js`) rather than silently producing two identically-named feeds.
- `title` uniqueness is otherwise enforced **per category/bucket only** (two feeds can share a name if they're in different categories), and explicitly on user-driven rename (`renameFeed` throws on a collision) — the auto-sync path above uses disambiguation instead of throwing, since there's no user present to show an error to.
- **`url` (normalized) must be globally unique across all feeds, regardless of category.** Normalization (`normalizeFeedUrl` in `dbHelpers.js`): lowercases the host, treats `http`/`https` as equivalent, strips one trailing slash from the path. Deliberately does **not** lowercase the path or touch the query string (some feeds legitimately depend on `?format=rss`-style params) — so `www.` vs. bare domain, or a differing query string, are treated as genuinely different feeds and allowed through. Violating this throws `"This feed URL has already been added."`, caught in `Sidebar.jsx` and shown via `window.alert`.
- `order` is scoped per bucket (per `categoryId`); values may overlap numerically across different buckets since they're never compared cross-bucket.

**`articles`** — `{ id, feedId, title, link, isoDate, insertedAt, contentSnippet, imageUrl, ogImageChecked, read, readAt, saved, unsavedAt }`
- `id` = `` `${feedId}::${guid || link}` `` (a `TEXT PRIMARY KEY`, not an autoincrement number) — this is what makes refresh idempotent, and it's also used directly as the React list key and click-handler argument on the frontend, so it must stay a string. `guid` has any trailing `#fragment` stripped before use (`feedParser.js`) — some feeds reuse the same guid for a live-updated article but append an incrementing revision fragment each time it's edited (`...#0`, then `...#8`), which would otherwise make every edit look like a brand-new article. This only affects the identity/guid, never the `link` field itself, since some sites legitimately depend on a real fragment there for deep-linking.
- `insertedAt` is set once, at first insert — a fallback anchor for the retention rule below when `isoDate` is missing/unparseable.
- `readAt` is set the moment `read` flips `false → true` (i.e. on click-to-open; there's no separate "mark read" affordance, and no "mark unread" UI either, so the reverse transition never currently happens).
- `unsavedAt` is set the moment `saved` flips `true → false`.
- Refreshing a feed (`upsertArticles`) never overwrites an existing article — `read`/`readAt`/`saved`/`unsavedAt`/`imageUrl`/`ogImageChecked` are preserved permanently across refreshes; only genuinely new guids get inserted. `ogImageChecked` records when the background OG-image fetch was last attempted for this article (success or failure) — `NULL` means not yet attempted. The one exception to `imageUrl` being permanent: it is cleared when the feed is detected as icon-only (`clearArticleImagesForFeed`, on refresh) and by the feed-wide-image / tracking-pixel cleanup migrations — see Per-article images.
- `feedId` has `ON DELETE CASCADE` — deleting a feed automatically deletes all of its articles via the foreign key.

### Ordering (categories and feeds)

There is currently **no manual drag-to-reorder and no sort buttons** anywhere in the UI (both were built, then intentionally removed— see Design decisions below). Ordering is fully automatic:
- On **create**: new item is inserted at the alphabetically-correct position relative to the current order (not a full re-sort of everyone else).
- On **rename**: the renamed item is repositioned alphabetically among its current siblings (again, not a full re-sort).
- Moving a feed to a different category (drag-and-drop) **appends it to the end** of the new bucket — it is not re-alphabetized into its new home.
- A periodic "normalize" pass squashes fractional order values back down to clean sequential integers after each mutation, wrapped in a `db.transaction(...)` so it's all-or-nothing.

## Retention & Purge

Storage is bounded by actually deleting articles (not a view-level filter), via `purgeExpiredArticles(db)` in `server/src/retention.js` — wrapped by `dbLogic.js`'s `createDb(db)` factory with its `db` argument already bound, so existing callers (a plain `purgeExpiredArticles()`, no args) are unaffected. **Saved articles (`saved === true`) are always exempt**, regardless of age.

For every non-saved article, compute an anchor timestamp:
```
base   = isoDate if present and valid, else insertedAt
anchor = max(base, readAt if set, unsavedAt if set)
```
Deleted once `now > anchor + 30 days`. So: never-read articles expire 30 days after publish; read articles get 30 days from the moment they were read (not published); an article that was saved and later unsaved gets a fresh 30-day grace period from the moment it was unsaved, regardless of how old it already was — this guarantees an accidental unsave can never delete something with zero grace period.

**Trigger**: runs server-side inside `POST /api/refresh` (`server/src/routes/refresh.js`), so it fires on every manual Refresh and every auto-refresh tick, including the one that fires immediately on app mount (see Auto-refresh below). Because expired articles are actually gone, the browse list/Today/Read Articles need no extra date-range filtering. Read Later is entirely unaffected by retention, by design.

## Auto-refresh

A `useEffect` in `App.jsx` (mount-only, empty deps) calls the same `handleRefresh` the manual button uses, immediately on mount — this matters because a cold open after the tab was closed for a while would otherwise show stale data for the first interval period. It then starts a 15-minute `setInterval`. A `visibilitychange` listener **clears and recreates** the interval (not just skips ticks) on hidden/visible, so a backgrounded tab doesn't burn fetches, and becoming visible again restarts a fresh 15-minute countdown rather than resuming a possibly-already-elapsed one. Each tick is a single `POST /api/refresh` call — the server does the per-feed looping, fetching at most 10 feeds at a time (`settleWithConcurrency`) rather than all at once: harmless with a dozen subscriptions, but an OPML import can bring in hundreds, and firing every fetch (plus its DNS lookup and icon/image follow-ups) in the same instant risks timeouts and rate limits from hosts that serve many feeds.

`handleRefresh` takes an `explicit` flag that the interval tick alone sets to `false` (the button click and the mount-time call both default to `true`). This only controls whether already-read/un-saved articles get pruned from view (see Main content area's lingering-article paragraph above) — it has no effect on what gets fetched; every tick, explicit or not, re-fetches every feed the same way.

## Export & Import (OPML)

Client-side only (`web/src/data/opml.js`'s `buildOPML(categories, feeds)`, a pure XML-string function with `escapeXml` for `&`/`<`/`>`/`"`), unaffected by the storage migration since it only ever operates on already-loaded `categories`/`feeds` arrays. "Export OPML" button sits in the sidebar directly below "+ Add Category". Categories become `<outline text="Name">` wrappers containing one `<outline type="rss" text="FeedTitle" xmlUrl="FeedURL"/>` per feed. (The code still has a fallback path emitting an uncategorized feed as a top-level outline with no wrapper, from when that was possible — see Sidebar below — but every feed has a category now, so it's unreachable through normal use.) Subscriptions only — read/saved/timestamps/order don't survive an export. **Import** is described below.

### Import

**Import OPML** and **Export OPML** share one row in the Customization card, split down the middle by a hairline (`.sidebar-card-row-split`, two `.sidebar-card-half` buttons) rather than stacked — the two are a natural pair (get subscriptions out, get them back in) and sit at the same visual weight. Import is a hidden `<input type="file">` behind its half of the row (`.opml`/`.xml`). OPML is the only file format the app reads or writes — it's the interchange format every other reader (Feedly, Inoreader, NetNewsWire, …) exports — and the only feed formats parsed are RSS and Atom.

The work is split where the existing rules already live. **In the browser**, `parseOPML` (`web/src/data/opml.js`) turns the file into a plain outline tree — `[{ text, xmlUrl, children }]` — using `DOMParser` (no new dependency; it never fetches external entities) and rejects anything that isn't well-formed XML with an `<opml><body>`. Files over 2 MB are refused before being read, matching the body limit on the server route. **On the server**, `POST /api/import` (`routes/import.js`, mounted with its own 2 MB JSON limit *ahead of* the global 100 KB parser, which would otherwise reject a big list first) runs `planOpmlImport` and then `importOpml` (`dbLogic.js`):
- **Nesting is flattened** — the app's categories are one level deep — so a feed lands in its *nearest* enclosing folder. A nameless folder inherits its parent.
- **Feeds with no usable folder go to an "Imported" category**: ones at the top level, and ones under a folder named "Uncategorized", a reserved name here (see Design decisions) that other readers, Feedly among them, export. Every feed must have a real category, so it can't be left unfiled.
- **An existing category is reused** (case-insensitive, same rule as `addCategory`); a new one is created only when a feed is actually about to land in it, so a folder whose feeds were all duplicates doesn't leave an empty category behind. Folders differing only by case merge.
- **Every feed goes through the real `addFeed`**, so URL validation (`feedUrlProblem`, shared with `addFeed`) and duplicate detection (normalized URL — `http`/`https` and a trailing slash don't distinguish feeds) are the very same rules as adding one by hand. A duplicate of an existing feed *or of an earlier entry in the same file* (Feedly lets a feed sit in several collections) is skipped and counted, not an error.
- **The OPML title is kept**, made unique within its category and slotted in alphabetically like a synced title. A dead feed never refreshes, so without this an imported dead feed would sit in the sidebar showing its raw URL forever. The trade-off: like a manual rename, a kept title is never replaced by the feed's own title on a later refresh (see `syncFeedMetadata`). An entry with no title falls back to the URL placeholder and is named by its first refresh as usual.
- **All-or-nothing on an unexpected fault**: the whole import is one transaction. Expected per-feed problems (an `ftp://` URL) don't abort it; they come back in `invalid`.
- **Bounded input**: at most 5000 entries, folders nested at most 10 deep, names cut to 200 characters, URLs over 2048 rejected — the JSON is untrusted, so types are checked rather than assumed.

Afterwards the client reloads (new categories and feeds appear), starts a normal refresh-all in the background so their articles load — not awaited, since a big list takes a while, and per-feed failures surface in the existing refresh error banner — and shows a blocking `window.alert` summary, the same channel the app already uses for validation messages: how many feeds and categories were added, how many were skipped as duplicates, and the first five invalid entries (with a "…and N more"). A file with no feeds in it, or that isn't OPML, produces an alert instead of an import. Import is additive only; it never deletes or edits an existing feed.

## Sidebar (top to bottom)

1. **All Feeds** — clears any category/feed selection and switches to the plain unread browse list (what the removed "All" tab used to show).
2. **Today** — a digest, not a filter combinable with a category/feed selection (see Today below for details).
3. **Read Later** — saved articles, app-wide, ignoring whatever category/feed was previously selected (like Read Articles below) — regardless of read status or age, the only view unaffected by both the read-hides-it rule and the 30-day retention purge.
4. **Read Articles** — shows every article where `read === true`, app-wide, ignoring whatever category/feed was previously selected; sorts on `readAt` (not `isoDate`) — see Sort below.
5. Selecting any category, feed, or All Feeds exits Today/Read Later/Read Articles and switches to the plain unread browse list, scoped to whatever was selected (or unscoped, for All Feeds).
6. A visual divider.
7. A small uppercase **"Categories"** section label (`.sidebar-section-label`), only rendered if there's at least one category.
8. **Category list** (alphabetical, auto-ordered as described above). The whole row is the click target and carries the selected/hover highlight. **With a mouse**, clicking a category selects it and expands/collapses its feeds (no chevron), and a ✎ appears on hover right after the name. **On touch (phone, tablet — anything without hover)**, tapping a category only selects it; the *selected* category then shows a ✎ and a chevron (▸/▾) right after the name, and the chevron is what expands/collapses (unselected rows show neither, so to expand or edit a category you select it first; a category you expanded and then navigated away from stays expanded, but its chevron is hidden until you select it again). The same goes for a selected feed's ✎. Both buttons are 22px wide x 44px tall on touch, flush against each other and the name. The ✎ is an edit (✎) button opening an inline panel with rename + "Delete category" — which is refused (with a message naming the category) if it still has any feeds in it; there's no "Uncategorized" bucket for them to fall back into, so they have to be moved or deleted first (see Data Model). Categories start **collapsed by default** — nothing expands until its name is clicked, and this resets on every reload since expand/collapse state isn't persisted. That's a deliberate choice, not a gap — a clean, fully-collapsed sidebar on load was preferred over remembering per-category state.
9. **Feeds within each category** — each is a draggable button (drag onto a different category header to recategorize it — dropping is the only interaction; there is no drag-to-reorder within a list). Dropping outside any category (blank space) is a no-op: there's no "Uncategorized" drop target to decategorize onto anymore, so the browser's native drag-and-drop just snaps the feed back to where it was — nothing to build for that, it falls out of not registering a drop handler there. Every feed shows its icon (`feedImageUrl`, falling back to the same placeholder icon used in the article list if missing or broken — see Feed Icons) before its title. Each feed has its own edit (✎) button opening a panel with rename, a read-only display of the feed's actual RSS URL, and "Delete feed" (also deletes that feed's articles).
10. A **"Customization"** section label over a single rounded card (`.sidebar-section-card`) containing stacked rows: **Add category** and **Add feed** side by side (each opens an inline form under the row — Add category asks for a name; Add feed asks for a URL and a **Category** dropdown, defaulting to the selected category, else the selected feed's category, else the first — since every feed needs one), then **Import OPML** and **Export OPML** side by side (split by a hairline, `.sidebar-card-row-split`), then the **appearance control** (System / Light / Dark — see Appearance below). Grouping these together under one label/card, separate from "+ Add Category", was a deliberate request — see Design decisions; Import and Export sharing a row instead of stacking is a later refinement, also on request.

Every feed must belong to a real category — there is no "Uncategorized" concept anymore (see Design decisions for why it was removed). Adding a feed is only possible via a category's own "+" button, so with zero categories the only next step is **+ Add Category**; there's no path to create a feed with no category. Both `addFeed` and dragging a feed onto a category (`updateFeedCategory`) reject a missing or nonexistent `categoryId` server-side too (`requireCategory` in `dbLogic.js`), not just in the UI.

**Destination/selection persists across a reload, resets on a new tab** (`App.jsx`): `view`, `selectedCategoryId`, and `selectedFeedId` are read from `sessionStorage` on mount and written back on every change. `sessionStorage` is inherently per-tab and cleared the moment a tab closes, so this needs no manual "was this a reload or a fresh open" detection — it falls directly out of the browser's own semantics. A genuinely fresh session (new tab, nothing in `sessionStorage` yet) lands on **Today**, not All Feeds — chosen since Today being empty ("No articles today yet.") is a rare edge case in practice, so it's a better landing spot than a plain unread dump. `sort` is deliberately excluded from this persistence and always resets to "Newest first."

**All Feeds**, **Today**, and **Read Later** each show a right-aligned, monospaced unread/saved count (`counts` in `App.jsx`, `.sb-count` in the CSS) — hidden when zero. `all`/`today` count unread articles (matching each view's own filter); `saved` counts everything in Read Later regardless of read status, matching that view's own definition.

Both category and feed rename/create actions validate uniqueness (name, and — for feeds — normalized URL) and the reserved name, surfacing violations via a blocking `window.alert` fed by the API's `400 { error }` responses. Deletions require `window.confirm`.

## Today

A digest rather than a filtered list: unread articles published today (bounded by local-timezone midnight on the article's `isoDate`; an article with a missing/unparseable `isoDate` never appears here), grouped by category (`App.jsx`'s `todayGroups`, rendered by `TodayDigest.jsx`):
- Named categories are sorted alphabetically. The grouping code still has a fallback "Uncategorized" group it would append last if it ever found a feed with no category, but since every feed now must have one (see Sidebar/Data Model above), that group is unreachable through normal use — dead code kept as a harmless defensive fallback rather than actively relied on.
- Each group is capped to its **10** most-recent-or-oldest eligible articles, per the active Sort direction (see below) — Sort governs both which 10 make the cut and their order within the group.
- Each named category's heading is a button that jumps straight into that category's normal full unread list (exiting Today).
- Ranking is by recency, not popularity — RSS feeds carry no click/pageview data, and there's no reliable free source for a link's real internet-wide "hits."

## Main content area (top bar + article list)

**Top bar**, left to right:
- Search input — a text field on the left that filters across all stored articles (including already-read ones) in real time as you type, matching against `title` and `contentSnippet` (the snippet/description shown below the title in each row). When a query is active it overrides the active sidebar selection entirely — Today, category, feed, Read Later, etc. — and shows a flat date-grouped list of every matching article across all feeds, sorted by the current sort direction. Clearing the field (Escape key or the native × button) returns to whatever view was showing before. Implemented as a client-side `useMemo` filter over the already-loaded `articles` array — no new API endpoint or backend change needed, since all articles are already in memory.
- Sort dropdown: Newest first / Oldest first. Chooses only the *direction*; the *timestamp sorted on* is owned by the active view — `readAt` in Read Articles, `isoDate` everywhere else, including within each of Today's per-category groups and in search results.
- Refresh button — triggers `POST /api/refresh`, which re-fetches every subscribed feed concurrently server-side, merges new articles in, runs the retention purge, and returns an error count if any feed(s) failed. A feed that fails on its *initial* add is still kept (not rolled back).

There are no view tabs in the top bar — Today, Read Later, and Read Articles all live in the sidebar (see above).

**Scroll position resets on navigation** (`App.jsx`): switching `view` or the selected category/feed scrolls the content area back to the top — each destination has its own list with its own height, so an old scroll offset left over from wherever you were before is meaningless there. Keyed specifically on `view`/`selectedCategoryId`/`selectedFeedId` rather than on every state change, so it fires for All Feeds/Today/Read Later/Read Articles/category/feed switches but not for anything in the Customization card (Export OPML, the appearance control) or the sort dropdown, none of which change what's selected. Resets both `.main`'s own scroll (its independently-scrolling column above the 768px breakpoint) and the window's (the whole page scrolls together below it).

**Date-grouped list** (`ArticleList.jsx`): the browse list, Read Later, and Read Articles all split an already-sorted article list into contiguous same-calendar-day sections under a heading — "Today", then e.g. "July 10, 2026", "July 9, 2026" — instead of one flat list. Grouping uses whichever timestamp field the active view is already sorted on (`readAt` in Read Articles, `isoDate` elsewhere), so the groups and the sort stay consistent; flipping Newest/Oldest changes both the order *and* which day's articles surface first. Today's own per-category digest (see Today above) does **not** get date headings — every article there is already "today" by definition, so a repeated single heading per category would be redundant; it opts out by simply not passing a grouping accessor.

**Article item** (compact, see Visual design below): a `.article-item` is a single-line flex row — the feed's icon (40px; falling back to the shared placeholder, see Feed Icons), a title over a snippet (each ellipsized to one line; the title opens the real article in a new tab and marks it read on click — no separate "mark read" affordance), a right-hand column with the feed name (app's monospace data font) over the time (just the time — the date lives in the group heading above), and a save/★ toggle for Read Later, revealed on hover (always visible once saved, or on touch devices). Below 768px the row becomes a small grid instead — `[icon] [title (up to 2 lines) / byline] [★]`, with `.article-main` set to `display: contents`, the snippet hidden, and the feed name and time moved under the title as `Example Feed · 9:33 AM` — because the right-hand column would otherwise squeeze the title to a few words. Per-article photos can be brought back with the `SHOW_ARTICLE_PHOTOS` constant in `ArticleItem.jsx` (see Design decisions).

**A just-read or just-un-saved article lingers in place, greyed out, instead of vanishing immediately** (`App.jsx`): clicking a title marks it read right away — the sidebar's unread count drops immediately, it lands in Read Articles immediately, and its row picks up the existing muted `.article-item.read` title style — but the row itself stays exactly where it was in the browse list/Today digest **for as long as you keep looking at that same screen**. It only actually drops out once you either explicitly refresh, or navigate to a different destination/category/feed and come back — giving you a moment to reconsider before it's gone, without lingering forever once you've genuinely moved on. Un-saving from Read Later works the same way (loses its accent bar and shows ☆, but stays put). Mechanically, a `snapshot` (`id → { read, saved }`) backstops each list's live filter with an OR: an article counts as still-unread (or still-saved) if it's *live* that way, or if the snapshot says it *was* — so a live change alone can't remove it, only a fresh snapshot can. The snapshot moves in two different ways: an **explicit refresh** (the Refresh button, or this mount's own initial load) re-baselines it from freshly-fetched server data — the 15-minute background auto-refresh (see Auto-refresh below) deliberately does **not** count, so it can still add newly-published articles without silently pruning rows you're already looking at; separately, **changing `view`/`selectedCategoryId`/`selectedFeedId`** (switching screens) also re-syncs the snapshot, but cheaply, straight from whatever `articles` already holds client-side — no network round-trip needed, since navigating away and back is itself a clear enough sign that you've moved on.

## Appearance (light / dark)

The app supports both light and dark, and by default **follows the OS/browser appearance** (`prefers-color-scheme`). A **System / Light / Dark** segmented control at the bottom of the sidebar (below "Export OPML") lets you override that:
- **System** (default) tracks the OS automatically; **Light** / **Dark** force that appearance regardless of the OS.
- The choice **persists** in `localStorage` (`web/src/theme.js`) and is applied **before first paint** by a tiny render-blocking script, `web/public/theme-init.js`, loaded from `web/index.html`, so a forced Light/Dark doesn't flash the wrong theme on load. "System" is represented by the *absence* of the stored key, so that script only ever has to look for an explicit light/dark. (It's a separate file rather than inline so the server's Content-Security-Policy can stay `script-src 'self'` — see Security below.)

**Implementation**: colors are CSS custom properties defined once in `web/src/index.css` using the `light-dark()` function, with `color-scheme` driving which half each token resolves to. "System" leaves `color-scheme: light dark` (OS decides); forcing a mode sets a `data-theme` attribute on `<html>` that overrides `color-scheme` to `light` or `dark`. Because every token is a `light-dark()` pair, flipping appearance is a single `color-scheme` change — there's no duplicated dark-mode token block to keep in sync. The control itself exposes `aria-pressed` per option; full dark mode is treated as an accessibility/eye-comfort feature, not just aesthetics.

## Visual design ("Console")

The current visual identity is deliberately dense and focused rather than card-heavy — closer to Linear/Arc than to a typical "cards with shadows" feed reader. It was chosen from three prototyped directions (a from-scratch design-comparison artifact built with the app's own real content) — the other two (a softer Apple-materials look, and a serif-headline editorial layout) were rejected in favor of this one; see Design decisions.

- **Palette**: cool near-neutral greys (not pure grey — a slight blue-cool bias) with a single indigo/violet accent (`--accent`), strongest in dark mode. Replaces an earlier system-blue Apple-style accent. All tokens still flow through the `light-dark()` system described above.
- **Type**: a monospaced face (`--mono`, `ui-monospace`/SF Mono/JetBrains Mono) is used specifically for *data* — unread/saved counts, date-group headings, per-article times — so numbers and timestamps read as data rather than prose; everything else stays on the system sans.
- **Article rows are flush, not cards**: no border/shadow at rest; hovering a row raises a subtle surface fill + 1px inset hairline (`.article-item:hover`). A saved article gets a permanent thin accent stripe on its left edge (`.article-item.saved`), visible whether or not it's hovered.
- **Progressive disclosure of the save toggle**: the ★/☆ button is invisible at rest on pointer devices and appears on row hover or keyboard focus (always visible once an article is saved, and always visible on touch, since there's no hover to reveal it there).
- **Refresh is visually primary** — the only accent-filled button in the top bar, since it's the one action most likely to be reached for repeatedly.

## Design decisions worth knowing

A condensed record of the decisions that shaped the app and the reasoning behind them. The full chronological history is in the git log.

**Storage and data**
- **Server-side SQLite, not browser storage.** Subscriptions and read/saved state persist independent of the browser (`better-sqlite3`). Business rules (ordering, uniqueness, retention purge) live in the server, and the frontend's `data/` modules are thin API wrappers.
- **Database lives outside the project directory** (see Data Directory), so code updates never touch data and the file is easy to back up. A "choose a folder" picker was rejected as more machinery than a single-user local tool needs; an OS-appropriate default plus a `FEED_READER_DATA_DIR` override covers it.
- **Lightweight migrations** (see Migrations): SQLite's `PRAGMA user_version` plus an ordered list in `server/src/migrations.js`. A full migration framework was rejected as solving a multi-environment problem this app doesn't have. Data migrations run once, ever.
- **Feed URLs are globally unique**, not unique per category, because duplicates would carry independent read/saved state.
- **A feed's title is adopted from the RSS `<title>` only on first successful refresh**, so manual renames are never overwritten. Auto-synced titles that collide in a category get a `" (2)"` suffix.
- **Article identity ignores a trailing `#fragment` on the guid.** Some feeds revise a guid's fragment each time a live story is edited while the link stays the same; without this, every edit created a duplicate row. The `link` itself is never modified.
- **Every feed belongs to a real category.** There is no "Uncategorized" concept; deleting a category with feeds in it is refused, and the rule is enforced server-side (`requireCategory`), not just in the UI. A few defensive fallbacks for the impossible case remain as harmless dead paths.
- **Manual reordering and sort buttons were built and removed.** Only recategorizing by drag-and-drop remains. The data model still supports per-bucket ordering if the UI ever comes back.

**Feed fetching and images**
- **Fetching uses Node's built-in `fetch()`**, with the XML handed to `rss-parser` only for parsing. Some sites block `rss-parser`'s own HTTP stack by TLS/connection fingerprint regardless of headers.
- **A plain, honest `User-Agent` (`FeedReader/1.0`)** works better than a spoofed browser one: some bot-protection layers assume a browser-like client can run a JavaScript challenge and answer with an empty response instead of the feed. The fetcher detects challenge responses and empty bodies and reports a clear error.
- **Some sites block cloud IP ranges outright.** Header changes can't fix that. For a site with a public JSON news API, a site-specific fallback adapter (`server/src/espnNews.js`) reads the same stories from it. Residential proxies and challenge-solving were deliberately rejected, since they exist to defeat bot protection. The honest alternative is hosting from a non-data-center network.
- **Article rows show the feed's icon, not the article's own photo** (a `SHOW_ARTICLE_PHOTOS` constant in `ArticleItem.jsx` restores photos). Photos are still extracted and stored, so nothing is lost. A brief experiment with generated monogram tiles was dropped in favor of each feed's real logo.
- **Icons are discovered, not guessed** (`server/src/faviconResolver.js`): the site's homepage is fetched, its declared icon tags are read, and the result is validated (a real image, a plausible size, reachable over HTTPS) before use. Real feeds failed in many different ways (wide wordmark banners, empty 1×1 stubs, redirects to HTML, HTTP-only hosts that browsers' HTTPS-only modes block), and hand-picked per-feed overrides would have been endless. Re-discovery runs automatically about every 30 days, and a transient failure never downgrades an already-good icon.
- **Icon tiles use a fixed white background and `object-fit: contain`**, so dark-ink logos stay visible in dark mode and wide logos aren't cropped. Icons render at their natural size, clamped to 24–48px, so tiny favicons aren't blurred by upscaling.
- **Junk images are filtered.** A single image repeated across a whole feed (a social-share logo) marks the feed as icon-only (`feedWideImage.js`), and 1×1 tracking pixels are dropped (`trackingPixel.js`). `og:image` is fetched in the background for articles without an image, once per article, reading only the first 32 KB of the page.

**Behavior and UI**
- **Today ranks by recency, not popularity.** RSS carries no popularity signal, and the external options (per-publisher APIs, social-aggregator scores) cover too little of a typical feed list to be worth the dependencies.
- **Read/saved articles linger greyed out in place** until an explicit refresh or a navigation to another screen, instead of vanishing the instant you click, so you can reconsider. The background auto-refresh may add articles to the list but never removes them.
- **The server is authoritative for `readAt`**: `PATCH /api/articles/:id/read` returns the timestamp it computed, so a just-read article sorts correctly in Read Articles without a refresh.
- **Navigation state survives a reload but not a new tab** (`sessionStorage`), and the default view is Today. Sort direction always resets to newest-first.
- **Search is client-side**: the full article set is already in memory, so a case-insensitive filter over title and snippet is fast enough at personal-reader scale. No library, no body search.
- **OPML import splits responsibility deliberately**: the browser only parses the file into an outline tree; every rule that can go wrong (flattening, duplicate detection, URL validation, the reserved name) lives server-side and reuses `addFeed`/`addCategory`, so bulk import can't drift from adding one feed by hand. Refresh-all fetches at most 10 feeds at a time.
- **Keyword feed search was considered and not built**, because it would require depending on, and disclosing the user's interests to, a third-party search service. See Future enhancements for what isn't ruled out.
- **Visual identity ("Console")** was chosen from three prototyped directions built from the app's real content. System/Light/Dark appearance is a sidebar control layered on CSS `light-dark()`.
- **Mobile uses an off-canvas drawer** (a CSS-only closed state that also removes it from the tab order), 44px touch targets, 16px inputs (iOS zooms on focus below that), hover styles gated behind `(hover: hover)`, and a compact two-line row. On touch, tapping a category only selects it; the selected row shows its pencil and chevron.
- **Payload and render cost were trimmed for phones**: gzip/brotli compression, a column-limited articles query, content-hashed immutable static assets, a 100-row initial render that grows as you scroll, lazy images and `content-visibility: auto`.
- **Customization card**: Add category, Add feed, Import OPML, Export OPML and the appearance control share one rounded card with segment-style buttons. Add feed has a Category dropdown because a feed must belong to a category.

**Deployment**
- **Cloud Run, single instance, SQLite on a mounted bucket, behind Identity-Aware Proxy** (see `DEPLOY.md`), because the app has no login of its own. Three env overrides keep local defaults unchanged: `HOST`, `ALLOWED_HOSTS` and `SQLITE_JOURNAL_MODE`.
- **A personal Gmail account hits "You don't have access"** with IAP's default Google-managed OAuth client even when every IAM grant is correct; a custom OAuth client fixes it.
- **No standalone installer.** A double-click launcher (`Feed Reader.command`) around the single-process server gets the day-to-day result for a fraction of the complexity; bundling `better-sqlite3`'s native module into a binary wasn't worth it.

**Testing**
- Logic that touches the database was split out of `db.js` (which opens the real database on import) into `dbHelpers.js` (pure) and `dbLogic.js` (`createDb(db)` factory), so it can run against throwaway in-memory databases using Node's built-in test runner with no extra dependencies. Network code is tested by mocking `fetch`. See Testing.

## Known gaps / not implemented

Missing pieces of work within the app's already-decided scope and design — not wishlist items still under consideration (see Future enhancements below for those). Ordered roughly from least to most work it'd actually take to close, not by importance.

**Medium** — a small, self-contained feature, not just a tweak:
- **Mark all as read** — close to a simple batch update; not yet decided on or built. (Unread/saved counts *are* now implemented — see Sidebar.)

**Larger** — needs a design decision or real architecture before it's just "write the code":
- Hosted deployment: a `Dockerfile` and `DEPLOY.md` cover Cloud Run (GCS-mounted SQLite, single instance, IAP for access). Feeds whose sites block cloud IPs fail there unless they have a fallback (one site does, see Architecture). There's still no process-manager config or HTTPS setup for self-hosting outside Cloud Run, and background refresh isn't server-side (refresh is client-driven, so feeds only update while a tab is open).

## Future enhancements

Features that are wanted in some form but not yet decided on or committed to the current design — distinct from Known Gaps above, which are missing pieces of already-committed scope. No timeline or priority implied by the order below.

- **Search for feeds by keyword ("find me cricket feeds") — deliberately not implemented, because it would require a third-party service.** This app's founding constraint is *no third-party services* (see the intro and README): everything it fetches comes from the publishers' own sites, nothing goes through anyone else's servers, and nothing about what you read or look for leaves your machine. Finding feeds *by topic or name* needs a searchable index of feeds, and RSS itself has no directory or search mechanism — so any implementation has to lean on someone else's service: a web search engine (needs an API key or paid tier, or scraping against its terms — and its results are web pages, not feeds, so a second step would still be needed to extract the feed from each one), or a feed-directory service such as Feedly's (to our knowledge only unofficial, undocumented endpoints exist for this, with no guarantee they stay available). Either one would (1) stop working whenever that provider changes or withdraws it, (2) put a log of your interests in a third party's hands — the opposite of "no tracking", and (3) bring API-key management with it. It's the same trade-off that ruled out popularity-based Today ranking (see Design decisions). Not ruled out: a **curated directory bundled in the repo** (no runtime dependency, but it only covers what someone curates and goes stale). Also a separate question, still open and needing no third party: **discovering a feed from a site URL you already have** (read the page's `<link rel="alternate" type="application/rss+xml">` tags, fetched through `safeFetch`) — that fixes "pasted a homepage instead of a feed URL" without any index.
- **Keyboard shortcuts** — considered, not yet decided on; needs an actual shortcut scheme designed first.
- **One automatic retry on an empty refresh response** — raised by a one-off refresh failure that turned out to be a transient empty body from the site's own CDN (see Design decisions), not a bug here. Not implemented since a single occurrence isn't evidence of a pattern worth the extra complexity; worth adding if it recurs, for this feed or others.

## Testing

`server/test/` (Node's built-in test runner — `npm test` from `server/`, i.e. `node --test test/*.test.js`; no new dependency). Deliberately scoped to the areas of the codebase where a bug wouldn't be obvious — logic that can silently regress without ever throwing, as opposed to something that would just crash or 404 immediately. A smoke test ("does the server start, does `GET /api/categories` return 200") wouldn't catch any of it, since the app keeps running and returning success the whole time it's quietly doing the wrong thing.

Built in phases, not all at once, in order of how much damage a regression would actually do:
- **`retention.test.js`** (9 cases) — `purgeExpiredArticles`'s anchor-timestamp logic: publish-date expiry, the `isoDate`-missing fallback to `insertedAt`, read articles getting 30 days from `readAt` instead of publish date, saved articles never expiring, an unsaved article's fresh grace period from `unsavedAt`, and the `max(readAt, unsavedAt)` precedence specifically (the case where an article would have expired on `readAt` alone but survives because `unsavedAt` is more recent).
- **`dedupe.test.js`** (5 cases) — the guid-fragment-merge migration's behavior: merging two fragment rows with no pre-existing base row, merging a fragment duplicate into an already-existing base row, `read`/`saved` OR'd together across the merged group (not overwritten by whichever row happens to apply last), the earliest non-null `readAt` kept, and a no-op check confirming it leaves unrelated articles untouched.
- **`dbHelpers.test.js`** (22 cases) — the pure ordering/uniqueness helpers with no database involved: `findAlphabeticalOrder`'s insertion math (middle/start/end of a sorted list, case-insensitive comparison, landing just after rather than before a case-insensitive match, excluding an id from the comparison on rename), `bucketOf`'s null/undefined-categoryId equivalence, `normalizeFeedUrl`'s deliberately asymmetric normalization (host lowercased but path/query left alone, http/https collapsed, exactly one trailing slash stripped, the root path *not* stripped down to nothing), and `uniqueTitleInBucket`'s disambiguation-suffix counting.
- **`db.test.js`** (28 cases) — the database-backed business rules via `dbLogic.js`'s `createDb(testDb)`: category/feed name uniqueness (case-insensitive, reserved-name rejection), `deleteCategory` refusing to delete a non-empty category, `addFeed`/`updateFeedCategory` rejecting a missing or nonexistent `categoryId`, feed URL uniqueness once normalized, per-category (not global) feed title uniqueness, `syncFeedMetadata`'s title-placeholder logic — including a direct regression test for the real "clobbered title" bug from earlier in this project's history (a later sync must never overwrite a title that's already real) — and `syncFeedMetadata` persisting `iconCheckedAt` on both first sync and later syncs (unlike `title`, which is placeholder-gated). Plus `clearArticleImagesForFeed` (used for icon-only feeds): clearing every stored image for a feed and reporting the count, preserving `read`/`saved` while doing so, and leaving other feeds' images untouched.
- **`faviconResolver.test.js`** (21 cases) — `extractIconCandidates`'s ranking (apple-touch-icon over plain icon, mask-icon deprioritized, largest declared size wins, malformed hrefs skipped) needs no network at all; `discoverFeedIcon`'s three rejection paths (wrong content-type, suspiciously small byte size, a candidate that redirects back down to plain HTTP) are exercised by mocking `global.fetch` with Node's built-in `mock.method` — canned responses simulating each of the real failure modes that broke real sites' icons, without any real network call; `shouldDiscoverIcon`'s date-math against a fixed `now` (never-checked, just-under/at/past the 30-day boundary) needs neither network nor database.
- **`feedWideImage.test.js`** (7 cases) / **`trackingPixel.test.js`** (4 cases) — the two pure junk-image detectors, no database or network: `dominantFeedImageUrl` flagging an all-same-logo feed (the all-same-logo case) while leaving genuinely per-article images alone, honouring the min-items/min-share thresholds and ignoring absent images; `isTrackingPixel` matching known tracking/spacer signatures (an `rss-pixel` filename, `/tracking/`, `1x1`, spacer gifs) without swallowing a real photo whose URL merely contains one of those words (`pixelated-art.jpg`).
- **`clearFeedWideImages.test.js`** (4 cases) / **`clearTrackingPixels.test.js`** (3 cases) — migrations 6 and 7 invoked directly against seeded rows: clearing the offending image while preserving `read`/`saved`, leaving genuine images untouched, and idempotency on a second run.
- **`opmlImport.test.js`** (18 cases) — `planOpmlImport`, pure: each feed filed under its folder, top-level feeds falling to the "Imported" category, nesting flattened to the nearest folder, the reserved "Uncategorized" name treated as no folder (and a nameless or reserved subfolder inheriting its parent), case-only-different folders merging with the first spelling kept, titles whitespace-collapsed and truncated, non-http(s)/unparseable/over-long URLs reported instead of planned, outlines that are neither a feed nor a folder ignored silently, junk field types from an untrusted client tolerated, and the limits (non-array input, no feeds, more than 5000 entries — with exactly 5000 accepted — and folders nested too deeply).
- **`importOpml.test.js`** (16 cases) — `importOpml` against a throwaway database: categories and feeds created with correct counts, OPML titles kept and ordered alphabetically, a title-less entry left as the URL placeholder so its first refresh names it, an imported title surviving a later `syncFeedMetadata` (while the feed's icon metadata still syncs), same-title feeds disambiguated within a category but not across categories, an existing category reused case-insensitively and its existing feeds/read state left untouched, duplicates skipped both against existing feeds (using `addFeed`'s URL normalization) and within the file, no empty category left for an all-duplicate folder, invalid entries reported while valid ones import, a no-feeds file changing nothing, and — using a SQLite trigger to force an unexpected fault mid-import — the transaction rolling back everything that came before it. Plus a 500-feed import completing well inside a generous time budget.
- **`importOpml.test.js`** also holds 2 `upsertArticles` cases: a missing image is filled in on a later refresh, while an existing image and `read` state are never touched.
- **`itemImageUrl.test.js`** (5 cases) — `media:content` image selection: declared entries taken at their word (including a declared non-image whose URL looks like an image), an undeclared entry accepted only on an image file extension, and a leading video entry skipped to reach a later image entry.
- **`espnNews.test.js`** (6 cases) — `espnNewsApiUrl` mapping league RSS URLs to API paths and rejecting unmapped leagues, other pages on the same site and look-alike hosts; `parseEspnNews` producing RSS-format guids, keeping only `Story`/`HeadlineNews`, skipping entries with no id or link, and tolerating a malformed response.
- **`requestGuards.test.js`** includes `ALLOWED_HOSTS` cases: listed hosts accepted, `*` accepting any host, and the loopback-only default when unset.
- **`settleWithConcurrency.test.js`** (5 cases) — results in input order with `allSettled`'s shape regardless of completion order, a rejection captured without stopping the rest, never more than `limit` calls in flight (and actually reaching the limit), and an empty list / a limit larger than the list.

**Why this order**: retention purge and guid-fragment dedup actually delete or merge real article rows, so a regression there means lost read/saved state, not a cosmetic bug — those came first. Ordering/uniqueness and icon-validation don't destroy data if they regress, so they came after, once the higher-stakes coverage was in place.

**How it stays testable**: none of `retention.js`, `migrations.js`, `dbHelpers.js`, `dbLogic.js`, `feedWideImage.js`, `trackingPixel.js`, `opmlImport.js`, `settleWithConcurrency.js`, `espnNews.js`, or `faviconResolver.js` open a database connection (or, for the last one, make a real network call) at module scope — unlike `db.js`, which opens the real database as a side effect of being imported. `dbLogic.js`'s `createDb(db)` factory is the key piece for the business-rule tests: it takes the connection as a parameter instead of closing over a module-level one, so `db.js` just calls it once against the real connection and re-exports the result, while tests call it again against a throwaway one. `test/helpers.js` bootstraps that throwaway database through the actual migration pipeline (`runMigrations`) rather than a hand-copied schema, so tests exercise the real current schema and can't silently drift from it. `migrations.js` exports its `MIGRATIONS` array (found by `name`, not index) so a test can invoke one migration's `run(db)` directly, and `faviconResolver.js` exports `extractIconCandidates` so its ranking can be checked without touching the network-dependent half at all.

### Frontend end-to-end tests

`web/e2e/` (Playwright, `npm run test:e2e` from `web/`). A real Chromium against the real built app and server, with a throwaway database: `web/e2e/seed.mjs` wipes `web/e2e/.data`, runs the server's own migrations, and seeds three categories, three feeds and 140 articles (130 in one feed, so the 100-row render window is exercised). The suite never touches the network or a real database: the fixtures abort every non-local request and stub the two refresh endpoints (the app refreshes on every load). Run through `playwright.config.js` on port 3101.

Why a real browser rather than a jsdom setup: the bugs this app is exposed to are CSS and media-query behavior (`hover: hover` vs `hover: none`, the 768px drawer breakpoint, `pointer: coarse` sizing). jsdom renders no CSS, so it can't see them. This was prompted by a real regression — a mangled CSS rule hid the selected category's pencil on touch screens through a deploy and a merge, and nothing caught it.

Two projects share one server: `desktop` (Chrome, 1280x800, mouse) and `mobile` (Chromium with the Pixel 7 profile: touch, no hover). `desktop.spec.js` and `mobile.spec.js` run in one project each; `shared.spec.js` runs in both. 35 tests in all:
- **desktop** — sidebar always visible with no menu button; click a category's name or the empty part of its row to select and expand/collapse it; no chevron; the pencil is hidden at rest, appears on hover right after the name, and opens the editor without toggling; the same for a feed's pencil; compact one-line rows.
- **mobile** — drawer closed at load with articles on screen; closes on backdrop, Escape and the close button; choosing any destination (even the active one) closes it; tapping a category selects without expanding and keeps the drawer open; only the selected category shows a pencil and chevron, 44px tall, narrow, touching each other and the name; the chevron expands/collapses; tapping a feed closes the drawer and only the selected feed shows a pencil; compact stacked rows with a 44px star; tapping a row opens the article and marks it read; tapping the star saves without opening it.
- **both** — no script errors on load; Add feed defaults its category to the selected one; Add category / Add feed highlight while their form is open and swap; adding a category works; the four Customization buttons match the appearance control's radius, weight, font size and height; forcing Light/Dark updates both `theme-color` metas and System restores them; All Feeds renders 100 rows and grows on "Show more"; images are lazy and rows show feed icons, not photos.

Tests share one database, so they use unique names and avoid asserting exact totals that other tests can change (`Add category` adds one that persists for the run). To confirm the suite actually catches regressions, the original pencil bug was reintroduced temporarily: three mobile tests failed.

CI (`.github/workflows/ci.yml`) installs Chromium and runs this suite after the backend tests and frontend lint/build; on failure it uploads the HTML report and traces as an artifact.

## Running it

**Double-click launcher** (`Feed Reader.command`, repo root): the easiest day-to-day option — no terminal typing required. Double-clicking it in Finder opens a Terminal window that starts the app (`npm start` under the hood) and, once it responds, opens `http://localhost:3001` in your default browser automatically. If the app is already running, it just re-opens the browser instead of starting a second instance. Leave that Terminal window open while you use the app — closing it (or Ctrl+C) stops the server. It's a plain shell script (no bundling, no installer, no native dependencies of its own), executable via its own file permission bit, checked into the repo like any other file — see Design decisions for why this was chosen over a true bundled/standalone executable.

**Network binding**: the server binds `127.0.0.1` by default, not `0.0.0.0`, so it accepts connections only from this machine. The API has no authentication of any kind — it doesn't need it, since the only intended client is this machine's own browser — which means binding every interface would have handed anyone else on the same network (shared Wi-Fi, an office LAN) full read/write access to every route, including feed deletion, which cascades to all of that feed's saved articles. `http://localhost:3001` is unaffected: browsers and `curl` fall back from IPv6 `::1` to IPv4 loopback automatically. The `HOST` env var overrides the bind address. Only a hosted deployment should set it (the Docker image uses `0.0.0.0`), and only behind something that authenticates every request (IAP on Cloud Run).

Binding to loopback isn't sufficient on its own, which is why `server/src/requestGuards.js` also checks the `Host` header on every request and accepts only `localhost`, `127.0.0.1` and `[::1]`. Without that check a DNS rebinding attack walks straight past both the loopback bind and the absence of CORS headers: a page on an attacker's domain re-points that name at `127.0.0.1` after loading, so its requests reach this server while the browser still treats them as same-origin and hands over the responses. The one thing such a page cannot forge is `Host` — scripts aren't permitted to set it — so it still names the attacker's domain. Only the hostname is checked, not the port, so the Vite dev proxy still works. `ALLOWED_HOSTS` (comma-separated hostnames, or `*` for any) extends the list for a hosted deployment. DNS rebinding is moot there only because IAP authenticates every request first. The Cloud Run service lists its two `run.app` hostnames.

The same file guards the two refresh routes (`POST /api/refresh`, `POST /api/feeds/:id/refresh`) with a required `X-Feed-Reader: 1` header, sent by `web/src/data/feeds.js`. Those two take no request body, which would otherwise make them the only state-changing routes any site could trigger through your browser: a bodyless POST is a "simple" cross-origin request and needs no preflight. Every other mutating route is already out of reach, being PATCH/DELETE or requiring a JSON body, both of which force a preflight this server never answers. A custom header forces that same preflight.

`server/src/securityHeaders.js` sets response headers on everything the server sends. The main one is a strict Content-Security-Policy (`default-src 'self'`, `script-src 'self'`, `style-src 'self'`, `connect-src 'self'`, with `img-src` widened to `data: https: http:` so feed icons and article images from any host still load). No XSS hole was found, but on this app one would be unusually costly — script on the app's own origin passes the Host check and can send the refresh header — and rendering full article HTML later is where XSS tends to appear, so the policy is in place ahead of that. The app earns a strict policy because it loads script and CSS only from its own origin; the previously-inline theme script was moved out to `web/public/theme-init.js` specifically so no `'unsafe-inline'` is needed. `frame-ancestors 'none'` plus `X-Frame-Options: DENY` is the clickjacking defence — nothing may frame the app, and nothing legitimately does. The CSP applies only to the Express-served build; the Vite dev server sets none, which is why the theme script's move to an external file (so `'self'` suffices) matters rather than a hash. Also here: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` (so the third-party image hosts don't learn the referring URL), and `X-Powered-By` is disabled. The unused `cors` dependency was removed.

**Single-process mode** (root `package.json`): `npm start` from the repo root runs `vite build` in `web/` (producing `web/dist`) then starts the server, which serves `web/dist` via `express.static` alongside the API — one process, one port (`http://localhost:3001`), no Vite dev server involved. The static-serving block in `server/src/index.js` only activates if `web/dist` exists (checked with `fs.existsSync`), so it's silently a no-op — just an informational console log — when it doesn't, which is what keeps this from interfering with the two-process dev workflow below. The launcher above is just this command with a one-time-typed, double-clickable wrapper around it.

**Two-process dev mode** (hot-reloading frontend):
```bash
cd server && npm start     # http://localhost:3001 — see Data Directory above for where feed-reader.db lives
cd web && npm run dev      # http://localhost:5173
```
Open `http://localhost:5173` in Firefox. Both must be running simultaneously; the web dev server proxies API calls to the backend. The backend has no hot-reload either way — restart it manually after any change under `server/src/`.

**Hosted (Cloud Run)**: the `Dockerfile` builds one image (the Express API plus the built frontend, on `node:22-slim` so `better-sqlite3`'s prebuilt binary works). `DEPLOY.md` covers the deploy itself: the GCS-mounted volume, `--max-instances=1` (SQLite on GCS FUSE has no real cross-process locking), IAP (including the custom OAuth client a Gmail account needs), and troubleshooting.
